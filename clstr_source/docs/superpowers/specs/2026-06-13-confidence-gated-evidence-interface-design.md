# Confidence-Gated Evidence Interface Design

## Purpose

CLSTR currently helps AppWorld dev57 slightly under the official-style executor, but it also causes regressions and increases execution failures. The next change should not add task-family rules. It should make skill evidence exposure reliable and benchmark-agnostic: CLSTR can select latent skills, but the executor should only see evidence when that evidence is likely to help.

This design introduces a confidence-gated evidence interface between CLSTR and downstream executors. It applies to AppWorld now, but the interface is framed around general concepts: evidence reliability, schema grounding, constraint preservation, transition availability, and fallback to the base executor.

## Non-Goals

- Do not add task-id-specific or AppWorld-family-specific rules.
- Do not encode special handling for Spotify, Venmo, file-system, or any other app.
- Do not train Qwen or replace the executor in this step.
- Do not start RL before the evidence interface is stable.
- Do not expose raw SkillX body, title, id, or `skill.md` text directly to the executor.

## Current Problem

The current official executor path works as follows:

1. CLSTR selects top-k skills at each executor step.
2. `build_verified_skill_handoff()` converts those selected skills into optional prompt evidence.
3. Qwen still writes free-form Python code.
4. Schema preflight blocks invalid APIs, but it cannot prevent semantic drift from weak or conflicting retrieved evidence.

This creates three failure modes:

- Harmful evidence: retrieved hints are schema-valid but semantically misaligned with the user goal.
- Empty evidence: all selected skills are suppressed, but the executor still sees a retrieval-related prompt block.
- Uncalibrated evidence: the executor receives hints without a step-level confidence decision that says whether CLSTR should be trusted, reduced to schema-only evidence, or ignored.

## Design Overview

Add a step-level evidence gate after CLSTR selection and per-skill verification.

```text
task + history
  -> CLSTR select top-k skills
  -> per-skill verifier/compressor
  -> step-level evidence gate
  -> one of:
       no_evidence_fallback
       schema_only_evidence
       workflow_hint_evidence
  -> executor prompt or tool/API predictor
```

The gate produces a structured `EvidenceGateDecision` and an executor-visible prompt block only when the decision allows it.

## Evidence Gate Inputs

The gate should use only benchmark-agnostic signals:

- CLSTR selection diagnostics:
  - selected scores;
  - score margin between top skills;
  - top-k agreement or disagreement;
  - ranking mode;
  - whether transition scores are available;
  - whether recurrent belief has prior state.
- Verifier/compressor diagnostics:
  - counts of `inject_hint`, `schema_only`, and `suppress`;
  - valid schema/API evidence count;
  - state-changing API evidence count;
  - suppressed evidence count and reason categories;
  - whether all selected evidence was suppressed.
- Task/executor schema signals:
  - required app/tool domains;
  - valid executable API/tool schema;
  - whether the task appears answer-seeking or state-changing at a generic level;
  - user constraints extracted as generic slots such as entity, date, source scope, ranking, count, threshold, destination, and action intent.
- Runtime signals:
  - previous execution failure count;
  - previous preflight failures;
  - repeated no-progress steps;
  - whether the latest output invalidates the previous evidence.

These signals must not depend on task ids, fixed app names, or manually listed AppWorld task templates.

## Gate Decisions

The gate has three public decisions:

### `no_evidence_fallback`

Do not include any retrieved-evidence block. The executor prompt must be byte-for-byte equivalent to qwen-only except for ordinary task/API docs context.

Use this when:

- all selected skills are suppressed;
- no schema-valid evidence remains;
- evidence is low-confidence or internally inconsistent;
- transition is unavailable and text-retrieval confidence is weak;
- evidence conflicts with user constraints;
- the gate has seen repeated execution harm from retrieved evidence.

### `schema_only_evidence`

Expose only valid APIs/tools and short schema-derived affordances. Do not expose workflow hints.

Use this when:

- selected skills agree on relevant APIs/tools;
- workflow text is incomplete or low-confidence;
- task intent is sensitive to user constraints;
- CLSTR confidence is moderate but not high.

### `workflow_hint_evidence`

Expose valid APIs/tools plus short workflow hints generated by the compressor.

Use this when:

- evidence has schema support;
- top-k selection is coherent;
- transition or belief provides meaningful prior-step context;
- workflow hints preserve all extracted user constraints;
- the evidence is likely to reduce executor search or recovery steps.

## Prompt Contract

The executor-visible block must be low salience and structured:

```text
[Optional Retrieved Evidence]
decision: schema_only_evidence | workflow_hint_evidence
confidence: low | medium | high
valid_tools_or_apis:
- app.api(...)
workflow_hints:
- ...
constraint_guard:
- preserve user entity/date/source/count/ranking/action constraints
raw_skill_text_omitted: true
```

For `no_evidence_fallback`, the block is omitted entirely.

## Diagnostics Contract

Every step should record:

- selected skill ids;
- selected scores and score margin;
- per-skill verifier decisions;
- gate decision and reasons;
- prompt-visible evidence text;
- whether prompt fallback was exact qwen-only fallback;
- transition availability;
- execution/preflight result after the decision.

This is needed for disagreement audits and for later RL.

## Relationship to RL

RL should not be the first fix. This gate makes the action space and rewards cleaner:

- action: choose evidence exposure level and possibly top-k evidence subset;
- reward: task success, execution validity, constraint preservation, no harmful state change, fewer recovery steps;
- regularization: stay close to frozen CLSTR/base executor when confidence is low;
- evaluation: train split only for optimization, dev for gates.

Once the deterministic gate improves or stabilizes dev57, RL can learn a policy over the same generic gate features. This preserves generalization because RL does not learn task-family rules; it learns when to trust retrieved evidence.

## Evaluation Plan

### Gate 0: CPU unit tests

- `no_evidence_fallback` omits the evidence block entirely.
- all-suppressed evidence falls back exactly to qwen-only prompt.
- schema-only decision never emits workflow hints.
- workflow hints must include raw-skill-text omission and constraint guard.
- diagnostics include selected scores, gate decision, and reasons.

### Gate 1: Existing dev57 disagreement subset

Use the nine disagreement tasks from the current qwen-only vs Stage4 dev57 comparison:

- keep the Stage4-only wins when possible;
- remove obvious qwen-only-only regressions when evidence is empty or low-confidence;
- no full dev57 rerun until this subset improves.

The implementation must not contain task ids or app-family rules for these nine tasks.

### Gate 2: Dev10 sanity

Run the existing dev10 official executor gate only if Gate 1 improves. Require:

- no increase in invalid API or preflight failures;
- no material increase in execution failures;
- success at least no worse than current Stage4 dev10.

### Gate 3: Dev57 rerun

Run dev57 only after Gate 1 and Gate 2 pass. Desired result:

- success improves over `27/57`, or
- success stays similar while execution failures drop materially from `177`.

## Paper Positioning

This mechanism is a reliability layer for large dynamic skill pools:

> CLSTR selects latent skills continuously over interaction steps, but deployment gates evidence exposure using schema grounding, transition availability, and constraint preservation. This prevents harmful retrieval from polluting the executor while preserving useful multi-step skill guidance.

The contribution remains CLSTR's continuous selection and coverage-aware routing. The gate makes the method deployable and general, rather than AppWorld-specific.

## Success Criteria

The design is successful if:

- no task-specific rules are introduced;
- low-confidence evidence can become exact base-executor fallback;
- Stage4-only gains are mostly preserved;
- qwen-only-only regressions caused by empty or conflicting evidence are reduced;
- execution failures decrease or stay controlled;
- diagnostics are sufficient to train a later RL gate policy.
